## Scaling and tuning

Same scenario on the development machine (18 vCPU, 15 GB RAM, everything in Docker on one host).

| n8n expression engine | Workers | Reply p50 / p95 | Worker CPU per run |
| --- | --- | --- | --- |
| isolated-vm (n8n default) | 1 | 16.3 / 27.9 s | - |
| isolated-vm | 4 | 7.8 / 18.6 s | - |
| isolated-vm | 8 | 5.0 / 12.9 s | 467 cpu-s |
| isolated-vm, isolate pool 4, compile cache | 8 | 2.9 / 4.8 s | 306 cpu-s |
| legacy (in-process) | 1 | 6.0 / 7.3 s | - |
| legacy | 2 | 2.4 / 4.2 s | - |
| legacy | 4 | 2.4 / 3.9 s | 73 cpu-s |

A CPU profile of a worker showed expression evaluation in V8 isolates as the main cost. The in-process
engine cuts worker CPU about 4x; it is used here because workflows are edited only by the platform admin
and client text never becomes an expression (see `docker-compose.yml`). Throughput then scales with
workers: `docker compose up -d --scale n8n-worker=N`. Messages are never lost either way: an overloaded
system only answers later.
